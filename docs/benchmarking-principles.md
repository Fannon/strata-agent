# Benchmarking principles

Companion to the [runner contract](benchmark.md) and the
[evaluation plan](evaluation.md). The contract says how the machinery works;
this note says why it works that way. Walkthrough-derived; judged and revised
later as needed.

## What a benchmark consists of

Four components, each failing in its own way:

1. **Tasks.** Concrete work with a defined starting state and a checkable end
   state: the input the agent sees, the environment it runs in, and the
   oracle — the independently established correct answer.
2. **Conditions (arms).** The setups being compared (`stock-pi`,
   `typed-quickjs`, `typed-bun`; unrestricted Bun remains deferred). All
   non-tested variables stay identical: model, settings, task text, budget.
3. **Metrics.** Per-run records: success, input/output/total tokens, tool
   call counts, wall-clock time, money, repair turns. Pass/fail alone discards
   the information needed to understand why an arm won.
4. **Grading.** The procedure turning a trace into a verdict. Versioned,
   tested with adversarial inputs (wrong final answer after a right
   intermediate one, timeout after an answer, malformed output), and run
   offline so grading is deterministic and free.

## Threats and practices

**Task selection bias.** Tasks chosen after the system is built reflect what
it already does well. Correction: freeze tasks before tuning (record the
freeze), split development tasks from held-out tasks, never edit held-out
tasks after scores are known — a later set is a new version, not a patch.

**Leakage.** Any path from question to answer that skips the work:
training-data contamination, expected answers on the candidate filesystem,
grader code in the working directory, prompts naming the tool sequence.
Correction: independent oracles (never generated by the measured adapter),
answers outside the candidate filesystem, method-neutral prompts, and a
canary — a planted marker whose appearance can provide evidence of access, with the detection mechanism and its limits stated. The
evaluator-access auditor (`benchmark/audit.ts`) scans recorded tool args for
answer/canary names and parent-tilde traversal on every trial; a per-cell
canary plus a policy flag keeps suspicious arguments visible, but neither guarantees detection or proves actual I/O. Independently enforced filesystem isolation can block specified answer paths; it does not eliminate all cheating or contamination. If adequate isolation cannot
be built, label the run a cooperative diagnostic, not a score.

**Grading weakness.** Substring matching passes wrong-shaped answers;
grading intermediate messages lets early guesses cover later failures;
timeouts and crashes counted as anything but failure inflate rates.
Correction: exact comparison (parsed-JSON deep equality) on the final
completed answer only. Timeout, nonzero exit, incomplete trace, and
malformed events are failures with subcategories — never successes.

**Stochasticity.** Single attempts confound arm quality with sampling luck;
warm-session reuse confounds it further (attempt two benefits from attempt
one's context). Correction: fresh independent sessions, counterbalanced
condition order, pinned model/provider/settings/versions. Two repeats may expose
flakiness but cannot establish stable rates; task diversity outranks repetition when budget is tight. Report
paired per-task differences with uncertainty, not bare means.

**Baseline fairness.** A restricted baseline measures nothing. Stock Pi keeps
shell pipelines, scripting, and normal file tools; every arm publishes its
full manifest (harness version, active tools, prompt additions, truncation
rules, extensions, model, settings). "Stock X" alone is underspecified.

**Accounting gaps.** Success rates without failure costs hide the price of
winning. Correction: cost per success including failures and retries;
missing usage stays null, never zero; budget reserved before requests, not
checked after.

**Goalpost movement.** Per-condition tuning after results, tasks added until
an arm fails, easy misses rerun until green. Correction: pre-registered
budgets, repetition counts, success bars, and stop rules. All outcomes
preserved, including embarrassing ones.

## Agent-specific concerns

- **Provider drift.** Identifiers change behavior over weeks. Pin the model
  string, snapshot prices per run, treat old results as historical.
- **Borrowed-task contamination.** Public task text may be in training data.
  Adaptations reduce but do not remove this; label adapted runs as adapted
  workloads, never official scores; check dataset licenses before copying.
- **Prompt-side costs.** Systems shrinking tool output while growing the
  prompt (generated declarations) must report both sides. Byte reduction
  here counts tool content only; declaration and source tokens are reported
  alongside.
- **Adherence as a separate verdict.** Correctness and tool adherence are
  graded independently: a typed-arm cell using bash is a violation with a
  correct answer, not a success. Pi tool restrictions and post-hoc checks are both implemented. They do not constrain direct Bun ambient access; answer correctness, tool policy, audit flags and containment remain distinct.
