# Structured final results and action recovery

Implemented October 1, 2026 under issues [058](../.work/issues/058-canonical-final-json.md), [053](../.work/issues/053-recovery-action-identity.md) and the narrow [052](../.work/issues/052-main-result-contract.md) prerequisite. These are shared production session/Pi features, with no model-name branches. The earlier experiments remain historical evidence; no paid benchmark accompanied this implementation.

## Select a computed result explicitly

A program still returns its computed JSON value from `main()`. Normal successful tool content remains `{result, program}`. To deliver that value as the final answer, the agent can:

1. Set `finalize: true` on `typed_program` when submitting the final computation; or
2. Call `finalize_result({program})` with the exact id returned by its latest successful program.

For example, the tool arguments can be:

```json
{
  "source": "import {api} from '@c/fixture'; export async function main(){return (await api.customers({country:'DE'})).customers.map(c=>c.id);}",
  "finalize": true
}
```

The host retains the successful result as compact JSON and selects it by identity. On the next normally completed assistant answer, Pi's `message_end` replacement hook delivers that exact JSON as the message's text. The completed event, agent state and persisted transcript agree. Provider usage and any original thinking blocks/signatures stay attached to the assistant message; result data is not regenerated by the model. Selection/delivery identities are recorded as `strata.final-result` custom entries and redacted `finalize` trace events.

The inline flag adds no separate tool-selection turn. Explicit `finalize_result` requires a tool call and the normal subsequent assistant finish. Neither path removes the normal final provider request. No paid measurements yet establish a token, latency or cost improvement. Streaming drafts may precede the final replacement; consumers requiring structured output should use the completed message, not intermediate deltas. Pi text print mode reads the completed state, while JSON event mode exposes the full event stream.

### Selection rules

- Selection is explicit: an ordinary successful program is never automatically the final answer.
- Only the latest completed successful program in the current user request can be selected. An earlier intermediate, failed, expired or previous-request result is refused.
- No selection while session work is running or the session is closed.
- Another program, capability load, other external tool, user Bash action or new user/steering request invalidates selection. `program_details` and `program_effects` inspection preserve it.
- Aborted, failed or truncated assistant completions invalidate selection rather than delivering stale data. Normal tool-call messages are left intact.
- Retained result JSON is immutable and bounded by existing result/report budgets, with at most 20 completed programs. It is cleared on shutdown and is not reconstructed from a resumed transcript.
- Selecting a result guarantees its serialization/identity, **not business correctness**. An empty or incorrect computation can still be explicitly selected. Uncertain service effects remain uncertain.

The programmatic equivalents are `session.beginTurn()`, `session.selectResult(program)` and the one-shot `session.consumeSelection()`. Non-Pi callers must start request scopes themselves and invalidate results when actions outside the session may change relevant state.

## Check known invalid returns before effects

The compiler now checks the inferred awaited root return type of zero-argument `main()`. It rejects known `void`, `undefined`, bigint, symbol or function results, including undefined branches, before running any capability calls. A program that only logs its answer receives a useful instruction to return it instead.

Normal inferred JSON returns need no extra annotations. `any`, `unknown`, assertions, nested non-JSON data, cycles and actual result size still require runtime validation; this is not a complete static serializability proof. `never` remains allowed for programs that do not return. Missing-return prevention does not validate business rules or guarantee complete pagination.

## Inspect actions after errors

`program_effects({})` returns paginated action evidence from retained programs in this user request. To inspect one specific retained program, including an earlier request, use:

```json
{"program":"<session>:p1","offset":0}
```

Each page returns up to five receipts, counts, `nextOffset`, a scope, `historyIncomplete` and allowed operations declared read-only for state inspection. Continue with `offset: nextOffset`. The tool reduces page size when necessary to preserve its byte budget; it never clips serialized JSON halfway through a record.

Each receipt identifies its exact program and broker call, capability/operation, effect classification, status, bounded input and—when accepted—bounded response. Inputs identify the requested target/value; responses can expose the new backend payment/action id. Pre-existing rows are not current-attempt receipts. Call ids are correlation ids, **not backend idempotency keys**.

| Status | Meaning | Recovery implication |
| --- | --- | --- |
| `confirmed` | Broker accepted a successful reply; `responseValidated` says whether an output schema was checked | The call was acknowledged; inspect business state when necessary to verify the requested meaning or asynchronous completion |
| `not-executed` | Local policy/input rejection or an explicit pre-effect resource denial | That call did not perform the effect; earlier calls may still have completed |
| `uncertain` | Dispatch began, but transport error, invalid reply, cancellation or missing completion prevents an accepted acknowledgement | Inspect current state before retrying; neither success nor failure can be inferred from this status alone |

Operations declared read-only do not create action receipts or copy their potentially large responses into the ledger. A missing `readOnly` hint is conservatively classified as `effect: "unknown"`; such an operation may actually be a read. Inspection operations are grant-filtered metadata hints, not independent verification of backend behavior. The agent calls them through the same typed API and broker.

Errors automatically include a small recovery summary from retained programs in this request, alongside diagnostics. This preserves evidence of successful earlier programs even if the current program is rejected before execution. Full pages are available with `program_effects`; `program_details` also includes one program's first receipt page. Successful program text stays quiet, and receipts are not copied into ordinary metrics or redacted developer trace files.

### Bounds and uncertainty

The ledger retains at most 20 programs, at most 100 receipt identities per program (matching the broker call limit), and 32 KiB of serialized evidence per program. Each input/response snapshot is bounded to 2 KiB; larger values carry a marked preview. Evidence can be omitted when its budget is exhausted, while action identities/status remain. Counts describe retained history; `historyIncomplete` flags eviction during the current request. Explicit requests for expired program ids fail rather than returning an empty success-looking history.

Receipts survive subsequent program/result failures. A cancelled run preserves accepted acknowledgements from its completed calls, while unfinished dispatches remain uncertain. Late transport responses do not rewrite an already completed receipt page. Restarting the session clears this in-memory ledger; there is no durable replay/idempotency system or automatic retry/rollback. Backend-supported idempotency identifiers can pass through existing typed input schemas and appear in receipts, but Strata does not synthesize support for services lacking it.

## Verification and evidence

Model-free tests exercise the production session, compiler, broker, QuickJS worker, actual pinned Pi SDK and a real local MCP subprocess:

- Missing/possibly missing root returns are rejected before simulated payment writes.
- Exact selected JSON replaces prose/fences and survives unchanged in completed events, state and persisted history; normal usage is preserved.
- Ordinary results remain unselected; later failures, other tools and new requests cannot deliver stale selections.
- New payment ids/amounts remain distinct from old same-target payments; no-effect rejections and transport/output uncertainty are separate.
- A payment made before an invalid MCP reply is visible in the ledger; recovery inspects it without replaying the write.
- Cancellation distinguishes completed acknowledgements from unfinished dispatches.
- Bounds, pagination, copies, retention and unvalidated-response provenance are checked.

Tests: [session/recovery](../test/integration/finalization-recovery.test.ts), [actual Pi SDK/MCP](../test/integration/pi-finalization.test.ts). These prove implementation behavior, not improved LLM task outcomes. The SDK test uses scripted local responses without provider access; mock token counts are not benchmark measurements. Package Pi remains pinned to 0.73.1. Installed Pi 0.99.1 benchmark compatibility was previously tested with experiment extensions, not certified for every full-extension feature here.

Earlier 049/051/054/060 source hashes and metrics describe their measured revisions. Production source changes here intentionally alter the compiler/session; reproduce an earlier campaign from its recorded revision rather than running its old matrix against today's changed sources. Frozen experiment definitions, published metrics and raw evidence are preserved.

## Subsequent real-model evidence

The [061 repeat](third-model-portability.md) ran 108 attempts across Muse, GLM and Ling with these features available in both arms. The audit verified exact selected JSON delivery in 105 attempts; `program_effects` was inspected nine times. This proves use in the measured experiment adapter, not a causal improvement versus an arm without these features or full Pi 0.99.1 extension certification.

Two Ling attempts returned the right credit answer without executing the credit action. Exact delivery and receipt visibility therefore remain distinct from verification of required business effects. The six reused workflows include invalid reads, not lost write replies; the model-free MCP/cancellation regressions above remain the stronger evidence for uncertain-write handling. [063](../.work/issues/063-effectful-completion-evidence.md) records a deferred caller-defined completion study. No new production behavior was selected by this run.
